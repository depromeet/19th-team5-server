# 토큰은 RS256으로 서명한다

승인 | 2026-11-24 | 관련 RFC: 없음

## 상황

core가 서명하고 realtime이 검증한다. 검증하는 realtime이 토큰을 만들 수 있으면 안 된다. 리뷰에서 "다른 비대칭 알고리즘과 비교한 근거가 있으면 좋겠다"는 의견이 나왔다.

## 결정

RS256(RSA 2048비트 이상)으로 서명한다. 개인키는 core만 갖고, 공개키는 `/.well-known/jwks.json`으로 공개한다. 헤더 `kid`로 키를 구분하고, 키 하나에는 알고리즘 하나만 쓴다.

## 이유

**대칭(HS256)을 뺀 이유**: 서명과 검증에 같은 비밀키를 쓴다. realtime도 비밀키를 가져야 하고, 그러면 realtime도 토큰을 만들 수 있다.

**비대칭 후보 비교**

| 알고리즘 | 서명 크기 | 주의점 |
| --- | --- | --- |
| RS256 | 256바이트 | 토큰이 길다 |
| PS256 | 256바이트 | RS256보다 이론상 안전하지만 지원이 조금 덜 보편적 |
| ES256 | 64바이트 | 서명마다 쓰는 난수(nonce)를 재사용하면 개인키가 드러난다. Java 15~18에는 가짜 서명을 통과시키는 취약점이 있었다 (CVE-2022-21449) |
| EdDSA | 64바이트 | Java에서 추가 의존성(Tink)이 필요하다 |

**RS256을 고른 근거**

1. 검증이 서명보다 훨씬 많다. 서명은 로그인·재발급·티켓 발급 때만, 검증은 요청과 연결마다 한다. RSA는 검증이 빠르다
2. RFC 9068 2.1은 발급 쪽과 검증 쪽 모두 RS256을 반드시 지원하라고 정한다. Spring(Nimbus)과 golang-jwt 모두 기본으로 다룬다
3. ECDSA의 난수 관리 같은 구현 함정이 적다

**실험** (2026-11-23, Apple M5, Java 17 + Nimbus 9.40, Go + golang-jwt v5.2.1, 코드: jwt-alg-lab)

토큰 한 개당 시간 (µs):

| 알고리즘 | Java 서명 | Java 검증 | Go 서명 | Go 검증 |
| --- | --- | --- | --- | --- |
| RS256 | 553 | 25 | 635 | 23 |
| PS256 | 554 | 27 | 638 | 22 |
| ES256 | 209 | 382 | 17 | 36 |
| EdDSA | 35 | 95 | 14 | 27 |

- RS256은 Java, Go 모두 검증이 가장 빠르다. 서명은 약 0.6ms로 가장 느리지만 서명은 드물다
- Java의 ES256 검증은 382µs로 RS256의 약 15배다. core도 요청마다 검증하므로 ES256이면 core 부담이 늘어난다
- 같은 클레임으로 토큰 길이는 RS256 694자, ES256 438자다. Authorization 헤더로 1KB 안쪽이라 문제없다

## 결과

- 얻는 것: realtime은 공개키만 가지므로 토큰을 위조할 수 없다. 검증이 빠르다. `kid` 기반이라 나중에 EdDSA 등으로 옮길 수 있다 (새 `kid`로 추가 → 발급 전환 → 옛 토큰 만료 후 제거)
- 감수하는 것: 토큰이 ES256보다 256자 길다. 개인키와 JWKS를 관리해야 한다 ([ADR-0010](0010-auth-signing-key-in-secrets-manager.md))
