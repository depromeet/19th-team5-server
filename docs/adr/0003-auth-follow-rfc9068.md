# 토큰 형식과 검증 규칙은 RFC 9068과 RFC 8725를 따른다

승인 | 2026-11-24 | 관련 RFC: 없음

## 상황

core(Java)가 발급하고 core와 realtime(Go)이 각자 검증한다. 필드 이름과 검증 순서를 우리끼리 정하면 두 언어의 구현이 어긋나기 쉽다. 리뷰에서 "OAuth를 쓰지 않더라도 충분히 논의된 표준 필드를 차용하자"는 의견이 나왔다.

## 결정

- 액세스 토큰 형식은 RFC 9068을 따른다: 헤더 `typ: at+jwt`, 클레임 `iss`, `aud`, `sub`, `client_id`(`"web"`), `iat`, `exp`, `jti`, 권한은 `roles`
- WebSocket 티켓은 같은 형식에 `typ: ws-ticket+jwt`를 쓴다
- 검증은 RFC 9068 4장 순서(`typ` → `iss` → `aud` → 서명 → `exp`)와 RFC 8725를 따른다
  - `alg`는 헤더를 믿지 않고 서버에서 RS256으로 고정한다
  - `jku`, `x5u`는 무시하고 키는 우리 JWKS에서만 받는다. `kid`는 그 목록 안에서 고를 때만 쓴다
  - `exp` 시계 여유는 60초 (RFC 7519 4.1.4)
  - RSA 키는 2048비트 이상 (RFC 7518 3.3)
- `aud`로 토큰마다 받는 서버를 나눈다. 액세스 토큰은 core, 티켓은 realtime
- OAuth 흐름(인가 코드 등)은 쓰지 않고 형식과 규칙만 빌린다

## 이유

- 표준을 따르면 Java·Go 라이브러리의 기본 검증을 그대로 쓸 수 있고, 두 서버가 문서 하나로 규칙을 맞춘다
- `typ`와 `aud`가 다르면 티켓을 액세스 토큰으로, 액세스 토큰을 티켓으로 쓸 수 없다
- `jku`를 따라가면 공격자가 자기 키 주소를 넣고 자기 키로 서명한 가짜 관리자 토큰이 통과한다. 발급처가 core 하나뿐이라 이 헤더가 필요 없다
- 시계 여유 60초인 이유
  - 발급한 서버(core)와 검증하는 서버(realtime)의 시계가 조금 달라도, 막 만료된 토큰을 잘못 거절하지 않으려고 둔다
  - RFC 7519 4.1.4는 `exp` 검사에 시계 차이를 감안한 작은 여유를 둘 수 있고, 보통 몇 분을 넘지 않는다고 한다
  - 여유가 길수록 만료된 토큰이 더 오래 통과한다. 서버는 NTP로 시계를 맞추므로 차이가 보통 1초 안이라 짧은 쪽인 60초로 했다
  - Spring Security의 `JwtTimestampValidator` 기본값도 60초라 core는 기본값을 그대로 쓴다. golang-jwt는 기본 여유가 0이라 realtime은 `WithLeeway(60 * time.Second)`로 맞춘다
- 버린 대안: 필드를 최소로(`sub`, `exp`만) 두기. 단순하지만 다른 용도의 토큰이 통과할 수 있다

**실험** (2026-11-23, jwt-alg-lab)

| 토큰 | 헤더 alg를 따르는 허술한 검증기 | Spring `NimbusJwtDecoder` (RS256 고정) | golang-jwt (`WithValidMethods` RS256) |
| --- | --- | --- | --- |
| 정상 RS256 | 통과 | 통과 | 통과 |
| `alg: none` | 통과 | 거부 | 거부 |
| 공개키로 HS256 서명 (키 혼동) | 통과 | 거부 | 거부 |
| 공격자 키 + `jku` 공격자 주소 | - | 거부 | 거부 |

- `alg`를 서버에서 고정하면 두 공격이 모두 막힌다
- Spring `NimbusJwtDecoder`는 기본 설정에서 `typ: at+jwt`를 거부한다 (`typ`가 `JWT`이거나 없을 때만 허용). `DefaultJOSEObjectTypeVerifier`로 `at+jwt`를 허용해야 한다
- golang-jwt는 `typ` 검사 옵션이 없어서 헤더를 직접 확인해야 한다

## 결과

- 얻는 것: 검증 실패 테스트 항목이 표준에서 바로 나온다. 알려진 JWT 공격을 라이브러리 설정으로 막는다
- 감수하는 것: 클라이언트가 웹 하나라 `client_id`는 고정값이다. RFC 9068이 권장하는 `scope`는 개념이 없어서 쓰지 않는다. 두 라이브러리 모두 `typ` 처리를 직접 설정해야 한다
