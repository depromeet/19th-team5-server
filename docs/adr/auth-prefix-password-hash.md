# 비밀번호 해시 앞에 알고리즘 이름표를 붙인다

승인 | 2026-11-24 | 관련 RFC: 없음

## 상황

비밀번호 해싱 알고리즘(BCrypt / Argon2id)은 배포 서버에서 측정해 정한다. 나중에 알고리즘이나 설정을 바꿔도 이미 가입한 회원이 로그인할 수 있어야 한다.

## 결정

저장하는 해시 앞에 `{bcrypt}`, `{argon2}` 같은 이름표를 붙인다. Spring Security `DelegatingPasswordEncoder`를 쓴다.

```
{bcrypt}$2a$10$Xk3f9...
```

## 이유

- 알고리즘을 바꿔도 기존 해시는 원문 비밀번호를 몰라서 한 번에 다시 해싱할 수 없다. 한동안 옛 방식과 새 방식이 DB에 섞인다
- 로그인 때 서버가 가진 건 저장된 해시 하나뿐이다. 그 값만 보고 어느 알고리즘으로 확인할지 알아야 한다
- `$2a$`, `$argon2id$`처럼 자기 표시가 있는 알고리즘도 있지만, PBKDF2나 SHA-256 해시는 16진수라 값만 봐서는 구분할 수 없다. `{id}` 규칙 하나로 모든 알고리즘을 같은 방식으로 처리한다
- `{bcrypt}`는 Spring이 어느 인코더로 넘길지 읽는 이름표이고, 안쪽 `$2a$10$`은 BCrypt가 자기 버전과 cost를 읽는 표시다. 역할이 다르다
- 버린 대안: 알고리즘을 별도 컬럼에 저장. 테이블 변경이 필요하고 컬럼과 해시가 어긋날 수 있다. Spring 기본 설정(`PasswordEncoderFactories.createDelegatingPasswordEncoder()`)도 처음부터 이름표를 붙인다

## 결과

- 얻는 것: 알고리즘을 바꿔도 마이그레이션 없이 넘어간다. 새 가입자는 새 알고리즘으로, 옛 회원은 로그인에 성공했을 때 원문으로 다시 해싱해 점진적으로 옮긴다. 그래서 알고리즘 결정을 측정 뒤로 미뤄도 위험이 작다
- 감수하는 것: 해시가 몇 글자 길어진다. 컬럼 길이를 여유 있게 잡는다
