# 리프레시 토큰은 DB에 저장하는 랜덤 문자열로 만들고 쓸 때마다 교체한다

승인 | 2026-11-24 | 관련 RFC: 없음

## 상황

액세스 토큰은 30분이라 리프레시 토큰(14일)으로 다시 받는다. 리프레시 토큰은 수명이 길어서 털리면 14일 동안 새 액세스 토큰을 뽑아 쓸 수 있다. 우리 웹 프론트는 비밀을 숨길 수 없는 공개 클라이언트(public client)라서, 서버는 리프레시 토큰 하나만 보고 재발급할 수밖에 없다. RFC 9700 4.14는 이런 클라이언트에 "기기에 묶기" 또는 "쓸 때마다 교체(Rotation)"를 요구한다.

## 결정

- 리프레시 토큰은 랜덤 32바이트로 만들고 HttpOnly 쿠키로 준다. DB에는 SHA-256 해시만 저장한다
- 재발급할 때마다 새 토큰으로 바꾸고 옛 토큰은 폐기한다 (Rotation)
- 폐기된 토큰이 다시 오면 같은 묶음(`family_id`, 로그인 1번 = 묶음 1개)을 전부 폐기한다 (재사용 감지)
- 폐기 사유를 `revoke_reason`(`ROTATED`, `LOGOUT`, `REUSE_DETECTED`, `PASSWORD_CHANGED`, `WITHDRAWN`)으로 남긴다
- 여러 탭
  - 브라우저는 `navigator.locks`로 한 번에 한 탭만 재발급한다
  - 서버는 `ROTATED`로 폐기된 지 10초 안에 온 옛 토큰을 탈취로 보지 않고 409 `REFRESH_IN_PROGRESS`를 준다. 새 토큰은 주지 않는다
- 재발급은 한 트랜잭션에서 `SELECT ... FOR UPDATE`로 행을 잠그고 "옛 토큰 폐기 + 새 토큰 저장"을 한다
- 재사용 감지 때 묶음 폐기는 401 예외와 함께 롤백되지 않게 별도 트랜잭션(`REQUIRES_NEW`)으로 커밋한다
  - 묶음 폐기 쿼리는 아직 살아 있는 토큰(`revoked_at IS NULL`)만 고친다

## 이유

- 기기에 묶기(DPoP, RFC 9449): 훔쳐도 쓸 수 없어 더 안전하지만 프론트·core 모두 구현이 복잡하다. RFC 9700은 "묶기 또는 Rotation"이라 Rotation만으로 표준을 지킨다
- JWT 리프레시 토큰: DB 없이 검증되지만 취소할 수 없고, 서명 키가 새면 리프레시 토큰까지 위조된다
- HttpOnly 쿠키는 훔치기 어렵게 할 뿐 공개 클라이언트라는 사실은 바꾸지 못한다. 그래서 쿠키와 Rotation을 둘 다 쓴다
- 해시를 BCrypt가 아니라 SHA-256으로 하는 이유: 토큰은 32바이트 랜덤이라 추측할 수 없다. 비밀번호처럼 느린 해시가 필요 없다
- 10초 유예: 액세스 토큰은 탭마다 따로 메모리에 있지만 리프레시 쿠키는 모든 탭이 공유한다. 유예가 없으면 두 탭이 거의 동시에 재발급할 때 정상 사용자가 재사용 감지에 걸려 모든 탭이 로그아웃된다. 클라이언트 잠금만으로는 이미 출발한 요청, 잠금 미지원 환경을 막을 수 없다
- 409인 이유: 401은 프론트가 "로그인 화면으로"라고 해석한다. 409는 "충돌이니 다시 시도"다
- `FOR UPDATE`가 없으면 두 요청이 모두 "살아 있다"고 읽고 둘 다 새 토큰을 발급해서 묶음이 두 갈래로 갈라진다
- 폐기 쿼리를 살아 있는 토큰으로 좁히는 이유: 바깥 트랜잭션이 `FOR UPDATE`로 잡은 행을 `REQUIRES_NEW` 트랜잭션이 고치려 하면, 바깥이 끝나기를 기다리는데 바깥은 안쪽이 끝나야 진행한다. 두 트랜잭션이 다른 DB 연결이라 DB가 교착 상태로 알아채지 못하고 잠금 대기 시간이 끝날 때까지 멈춘다. 잠긴 행은 이미 폐기된 토큰이라 `revoked_at IS NULL` 조건에서 빠진다
- 10초 유예는 표준에 없는 우리 규칙이다. 유예 중에도 옛 토큰으로 새 토큰을 주지 않으므로 RFC 9700을 어기지 않는다

## 결과

- 얻는 것: 로그아웃, 비밀번호 변경, 탈취 감지 때 리프레시 토큰을 바로 막을 수 있다. 서명 키가 바뀌어도 사용자는 재로그인 없이 재발급만 받으면 된다
- 감수하는 것
  - 재발급마다 DB 쓰기가 생긴다. 재발급 p99를 기록해 Redis 도입 판단 기준으로 쓴다 (초기 목표 200ms)
  - 탈취자가 10초 안에 옛 토큰을 쓰면 409만 받고 감지되지 않는다. 10초 뒤 다시 오면 묶음 전체가 폐기된다
  - 재사용이 감지되면 진짜 사용자도 다시 로그인해야 한다
- 확인할 것 (실험): 재사용 감지 때 묶음 폐기가 멈추지 않고 커밋되는지, 401 뒤에도 폐기가 롤백되지 않고 남는지
- 아직 정할 것: 새 토큰의 만료 시각. 첫 로그인 + 14일 고정(14일마다 재로그인, 더 안전)과 지금 + 14일 연장 중 구현 때 정한다
