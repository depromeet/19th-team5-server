# 비밀번호 해싱 동시 처리 제한은 측정한 뒤 넣는다

승인 | 2026-11-24 | 관련 RFC: 없음

## 상황

비밀번호 해싱은 일부러 느리게 만든 계산이다. 리뷰에서 "해싱 요청이 몰리면 CPU 부하가 커질 수 있으니, 서버가 감당 가능한 만큼만 받도록 제한하면 좋겠다"는 의견이 나왔다. 면접 시작 직전처럼 정상 사용자가 한꺼번에 로그인하면 CPU가 바닥나고, 로그인과 상관없는 API까지 느려질 수 있다. 다만 우리 서버에서 실제로 그런지는 아직 재 보지 않았다.

## 결정

- v1은 해싱 동시 처리 제한 없이 시작한다
- 배포 서버에서 아래 실험으로 먼저 잰다. 제한 없이 통과 기준이 깨지면 다음 순서로 넣는다. 단계마다 같은 실험으로 전후를 비교한다
  1. 해싱(회원가입, 로그인, 비밀번호 변경, 탈퇴 재확인)을 세마포어로 동시에 N개까지만 실행한다. 초기값 N은 CPU 코어 수, 부하 테스트에서 CPU 70% 안팎일 때의 값으로 조정한다. 자리가 없으면 최대 1초 기다리고(`tryAcquire(1, SECONDS)`), 그래도 없으면 `503 SERVICE_BUSY` + `Retry-After: 1`
  2. 1단계 뒤에도 기다리는 요청이 Tomcat 스레드를 다 차지해 기준이 깨지면, 기다리는 요청 수에도 상한을 두고 넘으면 바로 503을 준다
- 제한을 넣을 때는 이 ADR을 대체하는 새 ADR에 실험 숫자를 남긴다

## 이유

- 제한이 정말 필요한지 아직 모른다. 측정 없이 넣으면 효과를 증명할 수 없고, 사용자에게 503이라는 새 실패를 만든다
- 제한 없이 먼저 재고 기준이 깨질 때 넣으면, 같은 부하에서 전후 숫자로 효과를 보여줄 수 있다. 깨지지 않으면 필요 없는 장치를 넣지 않은 근거가 된다
- 나중에 넣기 쉽다. 해싱하는 곳이 한 곳뿐이고, 다른 서버와의 약속을 바꾸지 않는다. 프론트는 처음부터 503 + `Retry-After`를 처리해 둔다

넣게 되면 고를 방법:

| 방법 | 이 문제를 푸나 |
| --- | --- |
| IP·계정별 요청 제한 | 아니다. 공격자 한 명을 막는 장치다. 정상 사용자 100명이 동시에 오면 모두 통과한다 |
| 서버 늘리기 | v1은 서버 한 대다 |
| BCrypt cost 낮추기 | 빨라지지만 보안이 약해진다 |
| 해싱 동시 실행 수 제한 | 몇 명이 오든 해싱이 CPU를 다 먹지 못한다 (선택) |

- 위험한 작업을 칸막이에 가둬 전체를 지키는 벌크헤드(bulkhead) 패턴이다
- 해싱은 CPU 바운드라 코어 수보다 많이 돌려도 처리량은 늘지 않고 서로 느려지기만 한다. 그래서 코어 수가 출발점이다
- 대기열을 길게 두면 기다리는 동안 Tomcat 스레드(기본 200개)를 붙잡아 다른 API까지 모자라진다. 그래서 대기는 1초로 짧게 두고 빨리 실패한다
- 스레드 풀(`ThreadPoolExecutor`)로 격리해도 같은 효과지만, 해싱하는 곳이 한 곳뿐이라 세마포어가 단순하다
- 429가 아니라 503인 이유: 클라이언트가 많이 보내서가 아니라 서버가 지금 바빠서다

**실험 3** (2026-11-24, Apple M5, Java 17, Spring Security Crypto 6.3.4, 스레드 1개, JMH + `-prof gc`, 코드: password-hash-lab)

| 알고리즘 | 로그인 1번 시간 | 1번당 메모리 할당 | GC (측정 중) |
| --- | --- | --- | --- |
| BCrypt cost 10 | 105ms | 약 5.8KB | 0번 |
| BCrypt cost 12 | 421ms | 약 5.9KB | 0번 |
| Argon2id (19MiB, 2회, 병렬 1) | 37ms | 약 20.6MB | 25번 |

- BCrypt cost 10이면 코어 1개당 초당 약 9.5번 처리한다 (1 ÷ 0.105초)
- Argon2id는 해싱 1번에 약 20MB를 할당한다. 제한이 없으면 동시 20건에 약 400MB가 필요하다. 세마포어로 묶으면 동시에 해싱 중인 작업의 할당량이 N × 약 20MB로 묶인다 (2코어 약 40MB). 전체 메모리 상한은 아니다. 끝난 해싱의 메모리는 GC가 돌 때까지 남고 다른 작업도 메모리를 쓰므로, 실제 사용량은 부하 테스트에서 잰다
- Argon2id를 고르면 CPU뿐 아니라 메모리도 봐야 해서 제한이 필요할 가능성이 더 크다

## 결과

- 얻는 것: 필요가 확인된 장치만 넣는다. 넣게 되면 전후 숫자가 근거로 남는다
- 감수하는 것: 실험 전까지는 로그인이 몰리면 다른 API가 느려질 수 있다. 그래서 운영 배포 전에 실험한다
- 확인할 것 (실험): 실험 3은 노트북·스레드 1개 기준이다. 배포 서버에서 다시 재고, k6로 동시 로그인을 처리 한계(코어 수 ÷ 해싱 1회 시간)의 2배까지 늘려 가며 처리량, 503 비율, 로그인 p99, 내 정보 조회 p99를 잰다
  - 통과 기준: 내 정보 조회가 실패(타임아웃, 5xx) 없이 p99 1초 안에 응답한다. 제한을 넣었다면 넘친 로그인은 503으로 거절된다
  - 순서: 제한 없음 → (깨지면) N = 코어 수·×2·×4, 대기 0·1·5초 → (그래도 깨지면) 대기 수 상한
  - 해싱 자리를 기다리는 요청도 최대 1초 동안 Tomcat 스레드를 붙잡는다. 2단계를 판단할 때 스레드 사용량을 같이 본다
  - 2배는 "확실히 넘치는 양"이라는 뜻이다. 1.5배·3배여도 결론은 같아야 한다
