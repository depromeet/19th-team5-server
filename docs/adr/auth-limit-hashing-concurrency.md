# 비밀번호 해싱은 동시에 N개까지만 처리한다

승인 | 2026-11-24 | 관련 RFC: 없음

## 상황

비밀번호 해싱은 일부러 느리게 만든 계산이다. 리뷰에서 "해싱 요청이 몰리면 CPU 부하가 커질 수 있으니, 서버가 감당 가능한 만큼만 받도록 제한하면 좋겠다"는 의견이 나왔다. 면접 시작 직전처럼 정상 사용자가 한꺼번에 로그인하면 CPU가 바닥나고, 로그인과 상관없는 API까지 느려진다.

## 결정

- 해싱(회원가입, 로그인, 비밀번호 변경, 탈퇴 재확인)을 세마포어로 동시에 N개까지만 실행한다
- 초기값 N은 CPU 코어 수. 부하 테스트에서 CPU 70% 안팎일 때의 값으로 조정한다
- 자리가 없으면 최대 1초 기다리고(`tryAcquire(1, SECONDS)`), 그래도 없으면 `503 SERVICE_BUSY` + `Retry-After: 1`

## 이유

| 방법 | 이 문제를 푸나 |
| --- | --- |
| IP·계정별 요청 제한 | 아니다. 공격자 한 명을 막는 장치다. 정상 사용자 100명이 동시에 오면 모두 통과한다 |
| 서버 늘리기 | v1은 서버 한 대다 |
| BCrypt cost 낮추기 | 빨라지지만 보안이 약해진다 |
| 해싱 동시 실행 수 제한 | 몇 명이 오든 해싱이 CPU를 다 먹지 못한다 (선택) |

- 위험한 작업을 칸막이에 가둬 전체를 지키는 벌크헤드(bulkhead) 패턴이다
- 해싱은 CPU 바운드라 코어 수보다 많이 돌려도 처리량은 늘지 않고 서로 느려지기만 한다. 그래서 코어 수가 출발점이다
- 대기열을 길게 두면 기다리는 동안 Tomcat 스레드(기본 200개)를 붙잡아 다른 API까지 모자라진다. 그래서 대기는 1초로 짧게 두고 빨리 실패한다
- 스레드 풀(`ThreadPoolExecutor`)로 격리해도 같은 효과지만, 해싱하는 곳이 한 곳뿐이라 세마포어가 단순하다
- 429가 아니라 503인 이유: 클라이언트가 많이 보내서가 아니라 서버가 지금 바빠서다

**실험 3** (2026-11-24, Apple M5, Java 17, Spring Security Crypto 6.3.4, 스레드 1개, JMH + `-prof gc`, 코드: password-hash-lab)

| 알고리즘 | 로그인 1번 시간 | 1번당 메모리 할당 | GC (측정 중) |
| --- | --- | --- | --- |
| BCrypt cost 10 | 105ms | 약 5.8KB | 0번 |
| BCrypt cost 12 | 421ms | 약 5.9KB | 0번 |
| Argon2id (19MiB, 2회, 병렬 1) | 37ms | 약 20.6MB | 25번 |

- BCrypt cost 10이면 코어 1개당 초당 약 9.5번 처리한다 (1 ÷ 0.105초)
- Argon2id는 해싱 1번에 약 20MB를 할당한다. 세마포어가 없으면 동시 20건에 약 400MB가 필요하다. 세마포어로 묶으면 상한이 N × 약 20MB가 된다 (2코어 약 40MB)
- 어떤 알고리즘을 고르든 이 제한이 필요하다. BCrypt는 CPU를, Argon2id는 CPU와 메모리를 지킨다

## 결과

- 얻는 것: 로그인이 몰려도 서버가 감당할 만큼만 받고 다른 API는 영향을 덜 받는다. Argon2id를 골라도 메모리 상한이 생긴다
- 감수하는 것: 몰릴 때 일부 로그인이 503을 받는다. 프론트는 `Retry-After`를 보고 다시 시도해야 한다
- 확인할 것 (실험): 실험 3은 노트북·스레드 1개 기준이다. 배포 서버에서 다시 재고, k6로 동시 로그인을 늘려 가며 제한 없음 / N = 코어 수·×2·×4 / 대기 0·1·5초일 때 처리량, 503 비율, 로그인 p99, 내 정보 조회 p99를 비교한다
