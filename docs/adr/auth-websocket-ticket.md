# WebSocket은 일회용 티켓으로 인증한다

승인 | 2026-11-24 | 관련 RFC: 없음

## 상황

브라우저 WebSocket API는 `Authorization` 헤더를 넣을 수 없다. realtime은 연결한 사람이 누구인지 알아야 하고, 서버 한 대라 연결 자원을 아껴야 한다. 리뷰에서 "티켓 방식도 검토해서 비교해 보면 좋겠다"는 의견이 나왔다.

## 결정

1. 브라우저가 `POST /api/v1/auth/ws-ticket`을 액세스 토큰과 함께 호출한다
2. core가 30초짜리 일회용 JWT를 준다: `typ: ws-ticket+jwt`, `aud`는 realtime, `jti`는 고유값
3. 브라우저가 `/ws?ticket=티켓`으로 연결한다
4. realtime은 업그레이드 전에 티켓의 서명, `typ`, `aud`, `exp`를 JWKS로 직접 검증하고, 쓴 `jti`를 만료 + 시계 여유(60초)까지 메모리에 기억해 같은 티켓을 두 번 못 쓰게 한다
5. 실패하면 업그레이드하지 않고 HTTP 401로 거절한다

- 연결 후에는 티켓·액세스 토큰이 만료돼도 연결을 유지한다
- 브라우저 재연결: 열리기 전에 1006으로 끊기면 티켓을 새로 받아 다시 시도한다. 간격은 1초, 2초, 4초처럼 늘리고 jitter를 더하며 최대 횟수를 둔다. 티켓 발급이 401이면 액세스 토큰을 재발급하고, 그것도 실패하면 로그인 화면으로 보낸다
- 연결 후 오류는 종료 코드로 알린다: `4001 INVALID_TOKEN`, `4002 TOKEN_EXPIRED`, `4003 FORBIDDEN`
- realtime 접근 로그에는 쿼리 문자열을 남기지 않는다

## 이유

| 방법 | 문제 |
| --- | --- |
| URL에 액세스 토큰 (`?token=`) | 접근 로그와 브라우저 기록에 남는다. 30분짜리 토큰이라 로그를 본 사람이 그동안 사용자인 척할 수 있다 |
| `Sec-WebSocket-Protocol` 헤더 | 원래 용도가 아닌 꼼수다 |
| 쿠키 | 같은 도메인이어야 하고, Origin 검사가 없으면 다른 사이트가 연결을 만들 수 있다 (CSWSH) |
| 첫 메시지로 액세스 토큰 | 아래 비교 |

첫 메시지 방식과 비교:

| 기준 | 첫 메시지 | 티켓 (선택) |
| --- | --- | --- |
| 인증 전 연결 | 열린다. 아무나 연결만 잔뜩 열어 두면 realtime 메모리와 파일 디스크립터를 먹는다 | 안 열린다 |
| realtime으로 가는 것 | 30분짜리 액세스 토큰 | 30초 일회용 티켓 |
| URL에 남는 것 | 없음 | 티켓. 로그에 남아도 다시 쓸 수 없다 |
| 메시지 처리 | 모든 메시지에서 "인증된 연결인가"를 확인해야 한다. 빠뜨리면 구멍 | 연결 자체가 인증됨 |
| 재연결 시 core 필요 | 아니오 | 예 |
| 실패를 브라우저가 아는 방법 | 종료 코드 | 1006만 보인다 |
| realtime을 여러 대로 늘릴 때 | 변화 없음 | `jti` 저장소 공유 필요 |

- 인증 안 된 연결을 받지 않는 것이 가장 큰 차이다. realtime이 한 대라 연결 자원을 아껴야 한다
- core 의존은 "연결할 때 한 번"이고, 연결이 붙은 뒤에는 core가 없어도 된다
- 액세스 토큰이 realtime으로 가지 않으므로 액세스 토큰의 `aud`에서 realtime을 뺄 수 있다
- 1006 문제는 위 재연결 규칙으로 해결한다

## 결과

- 얻는 것: 인증되지 않은 연결이 열리지 않는다. realtime은 30초짜리 티켓만 본다. 메시지마다 인증 확인을 할 필요가 없다
- 감수하는 것
  - 연결할 때마다 core를 한 번 거친다. core가 멈추면 재연결도 안 된다
  - 업그레이드 실패 이유를 브라우저가 알 수 없다
  - `jti` 기억이 메모리라 realtime이 한 대일 때만 된다. 여러 대가 되면 Redis로 옮기거나 티켓 수명을 줄이는 새 ADR을 쓴다
- 확인할 것 (실험): 티켓 없이 / 만료된 티켓으로 / 같은 티켓 두 번으로 연결하면 모두 업그레이드 전에 거절되는지, 액세스 토큰을 `ticket` 자리에 넣으면 `typ` 검사로 거절되는지, 브라우저 `onclose` 코드가 실제로 1006인지
- 남은 질문: 면접 중 강퇴·탈퇴처럼 권한이 사라질 때 core가 realtime에 어떻게 알릴지
