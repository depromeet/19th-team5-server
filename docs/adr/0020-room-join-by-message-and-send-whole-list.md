# 면접방 입장은 연결 뒤 메시지로 하고, 참가자 목록은 바뀔 때마다 전체를 보낸다

승인 | 2026-11-27 | 관련 RFC: 없음

## 상황

WebSocket 접속 인증은 [ADR-0007](0007-auth-websocket-ticket.md)의 티켓으로 정했지만, 연결한 사람을 어느 면접방에 언제 들일지는 정하지 않았다. 함께 정할 것이 셋이다.

- 들어갈 방을 어떻게 고르는가
- 같은 계정이 한 방에 연결을 또 맺으면 어떻게 하는가
- 방에 누가 있는지를 클라이언트에 어떻게 알리는가

## 결정

- 연결이 열린 뒤 `room.join` 메시지로 방을 고른다. 참가자가 아니면 연결을 닫고 종료 코드로 이유를 알린다.
- 같은 계정이 같은 방에 새 연결로 들어오면 새 연결이 이전 연결을 대신하고, 이전 연결은 `4009 REPLACED`로 닫는다. 참가자 ID와 음성 연결은 그대로 두고, 음성 서버에도 다시 붙음을 알린다.
- 참가자 목록이 바뀔 때마다 목록 전체를 `room.participants`로 방의 모든 연결에 보낸다.

## 이유

- **연결 뒤 메시지로 입장:**
  - URL에 방을 실어(`/ws?ticket=...&interviewId=...`) 업그레이드 전에 거절하면, 브라우저는 실패 이유를 알 수 없다. 업그레이드 전에 거절된 연결은 `onclose`에서 `1006`만 보인다(인증/인가 설계 "WebSocket 연결 (티켓)"). 그러면 참가자가 아니어서 다시 시도해도 안 되는 경우와, 네트워크 문제로 다시 시도해야 하는 경우를 가를 수 없다.
  - 연결 뒤에 닫으면 종료 코드로 이유를 알릴 수 있다. RFC 6455 7.4.2절은 4000~4999를 "can be used by prior agreements between WebSocket applications"로 둔다. 인증/인가 설계도 참가자가 아닌 경우를 연결 뒤의 `4003 FORBIDDEN`으로 정해 두었다.
- **새 연결이 이전 연결을 대신:**
  - 실시간 서버는 ping에 pong이 없어야 끊긴 것을 알아채므로, 브라우저가 먼저 다시 붙을 수 있다. 새 연결을 거절하면 서버가 알아챌 때까지 다시 붙지 못한다. 이때 음성 서버에도 다시 붙음을 알려야 끊긴 사이 유실된 offer가 재전송된다.
  - 새 탭을 연 경우도 마지막 연결 하나만 남는다. 이전 탭은 `4009`를 받으면 다시 연결하지 않으므로 두 탭이 서로를 밀어내지 않는다.
- **목록 전체를 보냄:**
  - 한 방은 4명이라 목록 전체도 작다.
  - 입장·퇴장·끊김을 하나씩 알리면 클라이언트가 처음 목록에 바뀐 부분을 차례로 적용해야 하고, 하나를 놓치면 목록이 어긋난다. 전체를 보내면 마지막으로 받은 목록이 곧 지금 상태다.
  - 다시 붙은 클라이언트도 같은 메시지 하나로 지금 상태를 받는다.

## 결과

- 얻는 것:
  - 브라우저가 종료 코드만 보고 다시 연결할지 정한다.
  - 다시 붙는 흐름이 처음 입장과 같은 `room.join` 하나다.
  - 클라이언트는 참가자 목록을 합치는 코드가 없다.
- 감수하는 것:
  - 참가자가 아닌 사람도 WebSocket 업그레이드까지는 간다. 티켓 검증은 업그레이드 전에 하므로 인증되지 않은 사람은 아니다.
  - 목록이 바뀔 때마다 바뀌지 않은 참가자 정보도 다시 보낸다.
  - 같은 계정으로 두 탭에서 동시에 참여할 수 없다.
