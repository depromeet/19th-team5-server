# 서명 키는 Secrets Manager에 두고 메모리에만 올린다

승인 | 2026-11-24 | 관련 RFC: 없음

## 상황

RS256 개인키가 새면 누구든 아무 회원(관리자 포함) 토큰을 위조할 수 있다. 키를 어디에 두고 어떻게 서버에 넘길지 정해야 한다.

## 결정

- 담당자가 `openssl`로 RSA 2048비트 키를 만든다. 개발 키와 운영 키는 따로 둔다
- 개인키는 Secrets Manager에 둔다. core가 켜질 때 IAM 권한으로 받아 메모리에만 두고 디스크에 파일을 만들지 않는다
- 레포, 도커 이미지, 환경 변수 값, Notion, Discord에는 키를 두지 않는다
- Secrets Manager에는 키 목록과 지금 서명에 쓸 `kid`(`signing_kid`)를 함께 둔다. core는 켜질 때 목록의 공개키를 모두 JWKS와 자기 검증용 메모리에 올리고, 서명은 `signing_kid` 키로만 한다
- `kid`는 `YYYY-MM-keyN` 형식이다 (예: `2026-11-key1`)
- 6개월마다 수동으로 교체한다. 첫 운영 배포 전에 한 번 연습한다
- 교체 절차. 단계마다 Secrets Manager 값을 바꾸고 core를 재시작한다

  | 단계 | 할 일 | JWKS에 있는 키 | 서명하는 키 |
  | --- | --- | --- | --- |
  | 1. 올리기 | 목록에 새 키를 추가한다 | 옛 키, 새 키 | 옛 키 |
  | 2. 기다리기 | 10분 이상 기다린다 (realtime 5분 주기 갱신이 한 번 지나가도록) | 옛 키, 새 키 | 옛 키 |
  | 3. 바꾸기 | `signing_kid`를 새 키로 바꾼다 | 옛 키, 새 키 | 새 키 |
  | 4. 치우기 | 3단계에서 31분(액세스 토큰 수명 30분 + 시계 여유 60초) 이상 지나면 옛 키를 지운다 | 새 키 | 새 키 |

  - 단계마다 JWKS 응답의 `kid` 목록과, 새로 받은 토큰 헤더의 `kid`를 확인한다
- 유출 시에는 기다리지 않는다: 목록을 새 키 하나로 바꾸고 `signing_kid`도 새 키로 → core 재시작 → realtime 재시작

## 이유

보관 수준을 세 단계로 비교했다.

| 단계 | 방식 | 서버가 털리면 |
| --- | --- | --- |
| 1 | GitHub Secret → 서버에 파일(권한 600) | 키 파일을 복사해 간다 |
| 2 | Secrets Manager → 메모리 | 메모리를 뒤지면 가져갈 수 있다. 대신 디스크에 파일이 없고 접근 기록이 남는다 |
| 3 | KMS 비대칭 키로 서명만 요청 | 키는 못 가져간다. 침입한 동안 서명만 요청할 수 있다 |

- 1단계는 파일이 디스크에 남고 누가 언제 키를 읽었는지 기록이 없다
- 3단계가 가장 안전하지만 서명 코드를 KMS 호출로 바꿔야 하고 클라우드에 묶인다
- 그래도 다음 단계로 KMS를 고른 이유: KMS는 서명할 때마다 네트워크를 한 번 거치는데, 우리는 서명이 로그인·재발급·티켓 발급 때만 일어난다. 요청마다 하는 검증은 공개키로 메모리에서 하므로 KMS를 부르지 않는다. "서명은 드물고 검증은 잦은" 구조라 KMS 비용과 지연이 작다
- 2단계는 코드 변경이 시작할 때 키를 읽는 부분 하나라 지금 바로 할 수 있고, 1단계의 약점(디스크 파일, 기록 없음)을 없앤다
- 환경 변수에 키 내용을 넣지 않는 이유: `docker inspect`, `/proc/<pid>/environ`, 크래시 덤프로 쉽게 샌다

교체에 대해:

- 정기적으로 바꾸는 이유
  - 모르는 사이에 키가 샜더라도, 그 키로 위조할 수 있는 기간을 다음 교체까지로 줄인다
  - 유출 때 쓸 교체 절차를 평소에 연습해 둔다. 한 번도 안 해 본 절차를 급할 때 처음 하면 실수한다
  - 키가 깨질까 봐서가 아니다. RSA 2048은 NIST 기준 2030년까지 권장 범위다
- 6개월인 이유: NIST SP 800-57은 서명용 개인키를 1~3년마다 바꾸라고 한다. 우리는 수동 절차라 너무 드물면 방법을 잊고, 6개월이면 부담이 작다. 표준이 정한 숫자는 아니라 운영해 보며 조정한다
- 수동인 이유: 자동 교체는 core가 만든 개인키를 어디에 저장할지가 다시 문제가 된다. 파일은 재배포하면 사라지고, Secrets Manager에 쓰게 하면 core에 쓰기 권한을 줘야 한다. 6개월에 한 번이라 절차서와 알림으로 충분하다
- 새 키를 먼저 올리고 기다리는 이유: 바로 새 키로 서명하면 realtime은 모르는 `kid`라서 JWKS를 다시 받는다. 다시 받기는 1분에 한 번까지라, 직전에 한 번 받았다면 새 티켓(30초)이 최대 1분 동안 거절된다. 미리 올려 두면 realtime이 새 키를 이미 갖고 있다
- core 메모리에도 옛 공개키를 두는 이유: core는 JWKS를 읽지 않고 메모리의 공개키로 액세스 토큰을 검증한다. 옛 키를 일찍 버리면 옛 키로 서명된 토큰이 남은 수명 동안 401을 받는다
- 유출 때 realtime을 재시작하는 이유: 위조 토큰은 realtime이 이미 아는 옛 `kid`를 쓰므로 다시 받기가 일어나지 않는다. 재시작하지 않으면 다음 주기 갱신(최대 5분)까지 위조 토큰이 통과한다. 정상 사용자의 액세스 토큰도 무효가 되지만, 리프레시 토큰은 서명 키와 무관해서 재로그인 없이 재발급만 받으면 된다

## 결과

- 얻는 것: 디스크와 이미지에 키가 없다. 누가 키를 읽었는지 기록이 남는다
- 감수하는 것
  - 서버가 털리면 메모리의 키는 여전히 샐 수 있다. 다음 단계는 KMS이고, 그때 새 ADR을 쓴다
  - 교체는 수동이라 절차서와 알림이 필요하다
  - 교체 한 번에 core를 세 번 재시작한다. core가 한 대라 그동안 API가 잠깐 끊기므로 사용이 적은 시간에 한다
- 확인할 것 (실험): JWKS 응답에 `n`, `e`만 있고 개인키 값(`d`, `p`, `q`)이 없는지, 교체 1~4단계를 돌리는 동안 옛 키·새 키 토큰이 core와 realtime에서 모두 검증되는지(교체 연습), 3단계 직후 새 `kid` 티켓이 realtime에서 바로 통과하는지, 옛 `kid`를 빼면 realtime이 재시작 없이 최대 5분 뒤·재시작하면 즉시 옛 토큰을 거절하는지, 아무 `kid`나 적은 토큰을 연속으로 보내도 realtime이 JWKS를 1분에 한 번만 요청하는지
