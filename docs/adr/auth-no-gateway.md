# 게이트웨이 없이 core가 직접 요청 제한을 한다

승인 | 2026-11-24 | 관련 RFC: 없음

## 상황

로그인 무차별 대입을 막으려면 요청 제한이 필요하다. 보통은 앞단 게이트웨이나 프록시(Nginx 등)가 맡지만, 지금 구조에는 앞단이 없다. 학교 와이파이, 회사망, 통신사 CGNAT처럼 여러 사람이 IP 하나를 쓰는 경우도 고려해야 한다.

## 결정

- v1은 API 게이트웨이와 리버스 프록시를 두지 않는다. 불편해질 때 추가한다
- 로그인·회원가입 요청 제한은 core가 직접 한다. 넘으면 `429 TOO_MANY_REQUESTS`
- 기준을 나눈다

| 기준 | 목적 | 한도 |
| --- | --- | --- |
| 계정(이메일)별 실패 횟수 | 한 계정 비밀번호 대입 | 엄격. 넘으면 점점 늘어나는 지연 |
| IP별 요청 수 | 한 곳에서 여러 계정 대입 | 느슨하게 |

- IP는 연결의 remote address를 쓴다. `X-Forwarded-For` 같은 헤더는 믿지 않는다 (Spring `server.forward-headers-strategy`는 기본값 그대로). IPv6는 /64 단위로 센다
- 한도 값은 구현 때 정한다

## 이유

- 게이트웨이를 두면 서버와 설정이 하나 더 생기는데, 서버 한 대인 지금 그것이 해 주는 일은 요청 제한 정도다
- 앞단이 없으면 연결한 상대가 곧 클라이언트라 remote address를 그대로 믿을 수 있다
- `X-Forwarded-For`는 클라이언트가 아무 값이나 넣을 수 있어서, 믿으면 IP를 바꿔 가며 제한을 피할 수 있다
- IP 하나만 기준으로 막으면 공유 IP에서 한 사람의 실패 때문에 모두가 막힌다. 그래서 IP 한도는 느슨하게, 계정 한도는 엄격하게 둔다
- 계정 잠금 대신 지연을 쓰는 이유: 잠금은 남의 계정을 일부러 잠그는 공격에 쓰일 수 있다
- IPv6는 사용자 하나가 주소를 많이 가질 수 있다

## 결과

- 얻는 것: 구성 요소가 하나 적다. IP를 헷갈릴 여지가 없다
- 감수하는 것
  - 요청 제한 상태가 core 메모리에 있어서 core가 여러 대가 되면 서버마다 따로 센다
  - 앞에 로드밸런서나 프록시를 두는 순간 remote address가 그 장비 주소가 된다. 그때 "신뢰하는 프록시가 붙인 값만 믿는다"(엣지에서 `X-Forwarded-For`를 덮어쓰고, Spring은 `forward-headers-strategy=native`로 내부 IP만 신뢰)로 바꾸는 새 ADR을 쓴다
  - IP를 바꿔 가며 오는 대량 요청은 IP 기준으로 막지 못한다. 해싱 동시 처리 제한([결정](auth-limit-hashing-concurrency.md))이 2차 방어다
- 확인할 것 (실험): `X-Forwarded-For: 1.2.3.4`를 넣어도 제한이 우회되지 않는지, 같은 IP에서 계정 20개로 로그인할 때 정상 사용자가 막히는 시점
